## 2. P1.2 — Security and data-integrity repairs

All six items below were independently investigated against current code (not the missing audit) by a dedicated background agent per item, then fixed and tested in this session.

### 2.1 Last-owner deletion — was unguarded, now blocked at the database boundary

**Before:** `DELETE /api/workspaces/[workspaceId]/members` (`app/api/workspaces/[workspaceId]/members/route.ts:93`, pre-fix) had a check — `if (target.role==="owner" && auth.membership.role!=="owner")` — that could never fire, because `authorizeWorkspaceRequest({minRole:"owner"})` already guaranteed the caller was an owner by the time that line ran. Since `workspace_members_one_owner_idx` limits a workspace to at most one owner, the only reachable "owner-role target" is the caller's own row: **an owner could delete themselves with zero guard.** `workspace_members_cleanup_orphan` (a trigger from `0003_workflows.sql`) then deletes the whole workspace once it has zero members, and nearly every workspace-scoped table (`actions`, `action_runs`, `output_versions`, `deliveries`, `brand_profiles`, `locations`, `scan_snapshots`, `audit_events`, `workspace_usage`, …) cascades on `workspaces(id)` — so this was a full, silent, workspace-and-history-destroying self-service delete path.

**Fix:**
- `neon/migrations/0005_owner_removal_guard.sql` — new `BEFORE DELETE` trigger `workspace_members_prevent_owner_removal` on `workspace_members`, raising `owner_removal_forbidden` (SQLSTATE `23514`) whenever `OLD.role='owner' AND pg_trigger_depth()=0`. The `pg_trigger_depth()=0` condition scopes the block to a *direct* delete only — the legitimate cascade path (deleting `app_users`, which cascades to `workspace_members`, which lets the existing orphan-cleanup trigger remove the now-memberless workspace — exactly what `neon-schema.integration.test.ts`'s "retains member cleanup ... invariants" test already exercises) still works, because a cascade-originated delete runs inside the referencing table's own delete-cascade trigger machinery (`pg_trigger_depth() >= 1` there).
- `app/api/workspaces/[workspaceId]/members/route.ts` — added a 409 (`owner_removal_forbidden`) response when the target is the owner, ahead of the DB call (defense in depth / clean error instead of a raw exception); the pre-existing 403 branch (non-owner caller reaching an owner target, a hypothetical-loosened-gate case) is untouched.
- `scripts/neon/catalog.ts` — `verifyCatalog` previously asserted the *entire* trigger/function catalog is byte-identical to a frozen legacy-replay snapshot (`test/integration/fixtures/legacy-final-catalog.json`), which would reject any new migration's trigger/function outright. Added `additionalFunctions`/`additionalTriggers` allowlists (symmetric to the existing `deferredFunctions`/`deferredTriggers`) so genuinely new, post-migration-0004 schema objects are excluded from the legacy-parity `deepEqual` and instead asserted present by name — their actual behavior is proven by the dedicated tests below, not by the replay-fidelity check.

**Tests added:**
- `test/integration/neon-membership.integration.test.ts` — new test: direct removal of the sole owner rejects (`code:"23514"`), including a **concurrent double-removal attempt** (both reject, row and workspace survive). The pre-existing `it.each(["owner","manager","viewer"])` sign-in-mail test had its "owner" case removed (it previously removed the sole owner as an incidental step — no longer possible) and is now `it.each(["manager","viewer"])`.
- `app/api/workspaces/[workspaceId]/members/route.test.ts` — new unit test for the 409 branch, asserting the DB delete is never attempted.
- `test/integration/neon-schema.integration.test.ts` / `test/integration/neon-catalog.integration.test.ts` — updated expected trigger/function counts (7→8, 13→14) and the expected applied-migration list; two synthetic test migration names (`0005_probe.sql`, `0005_cancel.sql`) renamed to `0006_*` to avoid colliding lexicographically with the real new `0005_owner_removal_guard.sql`.
- **Not yet run against real PostgreSQL** — Docker is unavailable in this session (see §4). The migration SQL and `pg_trigger_depth()` semantics were reasoned through carefully against documented PostgreSQL trigger-cascade behavior and cross-checked against this repo's own existing use of the identical cascade path in `neon-schema.integration.test.ts`, but this is **not a substitute for actually running `db:verify` and `test:integration`**, which remain the authoritative gate. Recorded honestly as **blocked**, not passed.

### 2.2 SSRF in the website-check fetch — real, unmitigated gap; now closed

**Before:** `packages/scan-engine/src/collect-providers.ts:797` fetched the merchant-supplied `website_url` (public, attacker-influenced input from the scan-start API) with a raw `fetch(websiteUrl, {signal: AbortSignal.timeout(5000)})` — no scheme/host allowlist, no DNS/IP validation, default `redirect:"follow"`, no response-size cap. The repository's one existing SSRF guard, `lib/evidence/safe-media.ts`, is architecturally forbidden from being imported by `packages/scan-engine` (`evidence-media-boundary.test.ts` — it pulls in `sharp`, incompatible with the package's planned Cloudflare Worker target), so this path had no protection at all.

**Fix:** new `packages/scan-engine/src/safe-website-fetch.ts` — an independent, `sharp`-free reimplementation of `safe-media.ts`'s validation core (HTTPS-only, private/loopback/link-local IPv4+IPv6 rejection including embedded-IPv4 IPv6 forms, DNS-resolved-and-pinned connection via `node:https` with a custom `lookup`, every redirect hop re-resolved and re-validated rather than followed, 5 s timeout, 5 MB cap enforced via both `Content-Length` and streamed byte-count, non-HTML content-type rejected). Wired into `collect-providers.ts` in place of the raw fetch; a blocked/unreachable/oversized/non-HTML result leaves `website:{available:false}` — an honest "unavailable," never manufactured evidence that the page lacks an FAQ/H1/meta description.

**Tests added:** `packages/scan-engine/src/safe-website-fetch.test.ts` — 21 cases: private IPv4 (7 ranges), private IPv6 (5 forms incl. IPv4-mapped/NAT64), multi-address answers where any address is non-global, DNS-literal private hostnames, redirect-to-private (blocked, re-resolved), redirect-to-public (followed), too-many-redirects, non-HTML content-type, missing content-type, oversized declared `Content-Length`, oversized streamed body without a declared length, non-2xx status, empty/failed DNS resolution. All pass, alongside the existing 41 `evidence-media-boundary.test.ts` cases (confirming no forbidden import was introduced).

**Regression note:** this correctly broke one existing test's ability to intercept the website fetch via `vi.stubGlobal("fetch", ...)`, since the new fetcher deliberately does not use global `fetch` for its pinned request (that would defeat the pinning). Added a minimal, backward-compatible optional `deps.fetchWebsite` parameter to `collectScanProviders`/`runSerpAEO` (production callers — `lib/scan/run.ts`, `lib/scan/fixtures.ts` — never pass it; only the test does) and updated the one affected test (`app/api/scan/process/route.test.ts`) to inject a fake `fetchWebsite` instead.

### 2.3 Fail-open provider-spending routes — flipped to fail-closed

**Before:** the three routes that actually spend paid-provider budget — `POST /api/scan/process` (SerpApi/Places/RapidAPI via `collect-providers.ts`), `POST /api/business/search` (SerpApi), `POST /api/business/ig-search` (RapidAPI) — were **deliberately** configured `failClosed: false`, with an existing test literally titled "keeps scan processing available when a non-required limiter is unavailable" asserting that as intended. This directly contradicted the requirement that provider-spending routes fail closed when the rate limiter's own configuration is unavailable.

**Fix:** flipped all three to `failClosed: true`. `GET /api/scan/status` (read-only polling) was already, correctly, `failClosed: false` and is untouched.

**Tests:** `lib/security/rate-limit.test.ts`'s "keeps scan processing available" test was repurposed to `scan_status` (the scope that is legitimately fail-open) and a new test added proving `scan_process` now fails closed. `app/api/business/search/route.test.ts` updated to assert `failClosed:true`. ### 2.4 TLS enforcement — moved from a separate probe to the actual runtime pool

**Before:** `scripts/neon/readiness.ts` validates `sslmode`/`channel_binding` on `DATABASE_URL`/`DATABASE_URL_UNPOOLED`, but that is a **separate, read-only, deploy-time script** — it never runs against the actual request-serving connection pool (`lib/db/client.ts`'s `getPool()`), which builds its `Pool` from `readDatabaseConfig()`/`lib/db/config.ts` with no TLS check at all. A `DATABASE_URL` that passed readiness once could drift (redeploy, credential rotation, copy-paste) and serve real traffic with no verified TLS, and nothing in the runtime path would notice. (Live production logs do show a `sslmode` value present today — a `pg`/libpq deprecation warning about `prefer`/`require`/`verify-ca` aliasing to `verify-full` — so the *current* deployment is not actually exposed; the gap is the absence of enforcement, not a live incident.)

**Fix:** `lib/db/config.ts` — `readDatabaseConfig`/`validatedPostgresUrl` now reject (`database_configuration_insecure`) any application or migration URL without `sslmode ∈ {require, verify-ca, verify-full}`, gated to `NODE_ENV==="production"` only (matching the repo's existing convention in `lib/security/token-crypto.ts:38` for `OAUTH_TOKEN_ENCRYPTION_KEY`), so local/CI/test environments are unaffected.

**Tests:** `lib/db/config.test.ts` — 7 new cases (accepts no-sslmode outside production; accepts all three secure modes in production; rejects missing sslmode in production without leaking the URL/password; rejects `disable`/`allow`/`prefer`; rejects a secure app URL paired with an insecure migration URL). 17/17 pass.

## 2.7 P1.4 — Root-caused and fixed the live production Google/magic-link sign-in failure

The `verifier_exchange` stage (§1) turned out to be genuinely traceable locally, without needing hosted reproduction. `app/auth/callback/route.ts:40`'s `console.error(authDiagnostic("verifier_exchange", correlationId))` sits in a catch-all wrapping the whole handler, so the stage label alone doesn't pinpoint the failing call — but the handler only does one thing capable of throwing before any application logic runs: `new NextRequest(request)` (the pre-fix line 30).

**Root cause:** Next's compiled production route handler passes each route a `Proxy` wrapper around the native `Request`, not a plain `Request`. On Node 24, constructing `new Request(wrappedRequest, ...)` (a copy-construction) throws `TypeError: Cannot read private member #state from an object whose class did not declare it`, because the wrapper hides Undici's private internal fields from the copy constructor. This is not a hypothesis — it is the **exact same bug class already found and fixed once in this repository**, in the sibling route `app/api/auth/[...path]/route.ts` (commit `b991b7f`, "fix: forward wrapped Auth requests on Node 24," merged 2026-09-07), whose commit message names the identical mechanism. That fix was never applied to `app/auth/callback/route.ts`'s own `new NextRequest(request)` call, which remained vulnerable.

**Local reproduction (before touching any runtime code):**
```
node -e "const {NextRequest}=require('next/server'); const original=new Request('https://app.test/auth/callback?neon_auth_session_verifier=abc'); const wrapped=new Proxy(original,{get(t,p){return Reflect.get(t,p,t)}}); new NextRequest(wrapped)"
→ THROWS: TypeError Cannot read private member #state from an object whose class did not declare it
```
This is the same Proxy-wrapping technique `b991b7f`'s own test used to simulate the production route shape, run directly against this worktree's actual `next` install (`v16.2.6`) and Node (`v24.18.0`) — the same versions serving production.

**Fix:** `app/auth/callback/route.ts` — construct `NextRequest` from `request.url` (a plain string) plus explicitly copied headers, matching the pattern `proxy.ts:50` already uses correctly (`new NextRequest(request.url, {headers: validationHeaders})`) and the pattern `b991b7f` established for the sibling route. Verified the fix resolves the exact reproduction above. Confirmed via repo-wide grep that no other `new NextRequest(request)` / `new Request(request, ...)`-shaped copy-construction remains anywhere in the codebase — this was the one remaining unfixed instance.

**Tests:** `app/auth/callback/route.test.ts` — new regression test wraps a request in the same pass-through `Proxy` and calls the real `GET` handler (not just the raw reproduction), asserting it completes and forwards the wrapped request's URL/headers correctly to the (mocked) Auth middleware. 6/6 tests pass.

**What this does and does not establish:** this fixes a real, confirmed, currently-reproducing defect with strong local evidence (an exact TypeError reproduction plus a passing regression test using the production-shaped input). It does **not** constitute the "completed authorized hosted sign-in" the commissioning instructions ask for — that step requires a human (Willy) to interactively complete Google OAuth consent in a real browser, which is outside what this session can or should do (entering credentials / completing OAuth consent is a prohibited action for this agent regardless). Recommended next step: Willy attempts a real sign-in against the current production deployment (or a preview built from this fix) and confirms the callback now completes; if it still fails, the correlation ID and stage from that attempt will show whether a *different* cause is also present.

## 5. Findings from independent investigation of P1.3–P1.7 (not yet fixed)

Six background agents independently investigated every remaining Phase-1 requirement area against current code. Full findings are in this session's transcript; summarized here so the next work session can pick up without re-investigating:

**P1.3 (scan honesty):** coverage renders as a raw fraction ("Coverage 0.5%" instead of "50%") on the *scanning* page specifically (the report page is correct); the scanning page shows a "Measured" badge for collectors that are still pending; scan consent is pure client-side UI state with **zero server persistence or validation** — a direct `POST /api/scan/start` bypasses it entirely; polling has no bounded budget or stalled terminal state; and — the highest-value fix in this group — when a scan completes with usable evidence but under the 2-module composite threshold, `processor.ts` marks it `status:"failed"`, and `view-model.ts` then blanket-suppresses coverage/findings/module-scores for **any** `failed` job, showing a generic "scan didn't complete" screen even though purpose-built "score withheld: not enough independent evidence" copy already exists in `lib/copy.ts` and is simply unreachable dead code.

**P1.4 (identity/sign-in):** the unlock→sign-in handoff is fully implemented on the *receiving* end (claim/return-path parsing, open-redirect rejection) but the *emission* side is missing — no component actually renders a `/owner/sign-in?claim=` link on an unlocked report; Google-sign-in-vs-ownership-claim separation is correctly implemented; the sign-in failure is diagnosed (six-stage model) but not root-caused (see §1); a real bug exists in channel-dependent eligibility — WhatsApp/LINE/phone unlockers who supply a recovery email have it stored in a different table (`report_access_grants.email_normalized`) than the one the magic-link/self-service-claim eligibility checks query (`leads.email`), so they hit a silent dead end requesting a sign-in link on a new device; anti-enumeration is correctly implemented; the site-header sign-in button is `hidden` below the `lg` (1024px) breakpoint with no other mobile entry point, and the mobile Sheet/Dialog close button is hardcoded to English regardless of locale.

**P1.5 (onboarding persistence):** brand voice/approved claims typed in onboarding step 4 are POSTed but the claim-completion route (`app/api/workspaces/claim/route.ts`) never reads those fields — only an empty default `brand_profiles` row is ever created; the onboarding component's local voice enum (`"warm"|"concise"|"playful"`) doesn't even match the real schema (`BRAND_VOICES = ["warm","professional","playful","direct"]`) — "concise" isn't legal server-side. Owner-confirmed facts are correctly never silently overwritten. Onboarding resume depends on a transient `?claimed=1` query param rather than fully persisted server state (partial). Tamper resistance is solid (server-derived workspace attachment, no client-supplied workspace ID accepted).

**P1.6 (review-reply workflow):** the SQL approval/export core (`neon/migrations/0004_atomic_operations.sql`) is excellent — correctly locked, idempotent, concurrency-tested. The generation-triggering layer around it has real gaps: review sampling from scan evidence is implemented in the agent but the UI hard-codes manual re-entry as a required input regardless of available evidence; `agentKey` is checked against the registry of *all* agents, not the calling action's own template (a client could request an unrelated agent on any action); the execution-deadline math is wrong by design (a documented comment claims two 45 s LLM attempts fit in a 60 s function — that's 90 s); no mechanism ever writes the `timed_out` state that already exists in the schema, so an orphaned `running` action-run permanently blocks regeneration with no recovery; the Create-page flow doesn't check `state`/`factsNeeded` before declaring success (the Action-detail page does this correctly); no prompt-injection framing exists anywhere in the LLM prompt construction.
