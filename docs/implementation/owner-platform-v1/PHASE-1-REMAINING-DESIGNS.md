# Phase 1 — remaining items: designs and adversarial reviews

Produced by a 10-agent workflow (5 design + 5 adversarial verification), 2.4M subagent tokens, 0 errors. **Every plan came back `needs-change`** — do not implement any of them as written; apply the corrections first.

## Cross-cutting constraint confirmed by all five reviews

`scripts/neon/catalog.ts`’s `verifyCatalog()` deep-equals tables/columns/constraints/indexes against the frozen `test/integration/fixtures/legacy-final-catalog.json`, and the `additionalFunctions`/`additionalTriggers` allowlists cover **functions and triggers only**. A new column, table, constraint or index therefore cannot be added without rewriting that frozen fixture, so **all five items must be solved without a migration** — which all five designs independently concluded.

## Persist and validate scan consent server-side

**Verdict: needs-change** · design touches 14 files · migration needed: false

### Recommended approach

Reuse consent_records; do not write migration 0006. The schema genuinely allows it: consent_type is plain `text NOT NULL` with no CHECK constraint (neon/migrations/0002_business.sql:192-201; the frozen catalog confirms consent_records carries only consent_records_pkey plus the two FKs), so the new value 'public_evidence' needs no DDL; lead_id is nullable, which is exactly right because no lead exists at scan time; granted/policy_version/locale are NOT NULL and all three are known at scan start; and consent_records_job_id_idx already indexes the dispatch-gate lookup. job_id is NOT NULL with ON DELETE CASCADE, which forces the consent row to be written after the audit_jobs insert — solved by writing both inside one transaction so a queued job can never exist without its consent row, and it gives correct erasure semantics for free (deleting the job removes the consent, and lib/lifecycle/export-columns.ts already exports consent_records for DSAR). The decisive argument against a migration is that verifyCatalog() deep-equals the whole table/column/constraint/index catalog against the frozen legacy snapshot with no allowlist, so a new column or table would fail db:verify. Consent therefore becomes: the client sends `public_evidence_consent: true` plus the `consent_policy_version` string the page rendered; parseScanStartBody validates presence and exact equality with resolveConsentPolicyVersion(process.env.REPORT_CONSENT_POLICY_VERSION) before any database work; jobsRepository.insert writes audit_jobs and the consent_records row atomically; and POST /api/scan/process re-reads the row before spending a cent on providers, marking the queued job `failed` (a legal queued→failed transition, no new status value) so the scanning page's existing failure card surfaces it instead of polling forever.

### Defects found by adversarial review (fix before implementing)

1. TYPE/TEST CONTRADICTION — lib/scan/start-job.ts: the plan declares `ScanStartParse` failure as `{ ok:false; error:string; status?: 409 }` but says parseScanStartBody returns parseScanConsent's failure "verbatim", and parseScanConsent's failure type is `{ ok:false; error:string; status: 400 | 409 }`. `400` is not assignable to `409 | undefined`, so `tsc --noEmit` fails. Worse, the plan's own new test `expect(parseScanStartBody({...validBody, public_evidence_consent: undefined })).toEqual({ ok:false, error:'public evidence consent is required' })` fails at runtime too, because the returned object carries the extra `status: 400` and the existing failure assertions in lib/scan/start-job.test.ts:69/73/74 use exact `toEqual`.

2. UNMENTIONED BREAKING CALLER — tests/neon-scan-unavailable.test.ts:17 calls `buildScanStartPayload(draft, "zh-HK")` with two arguments. tsconfig.json includes `**/*.ts` (excluding only node_modules and packages), so the new required third parameter is an immediate `pnpm typecheck` failure. It breaks a second time at runtime: line 18 POSTs that payload to the real `app/api/scan/start/route.ts` and asserts `status === 503` (the redacted-persistence-failure contract); with no consent in the body the route now answers 400 and the assertion, plus the `not.toContain("password")` guarantee it protects, silently stops being exercised. The file is absent from the plan's `files` and `tests` lists.

3. UNMENTIONED BREAKING CALLER — test/integration/neon-scan-start.integration.test.ts:66 builds a raw object literal for `parseScanStartBody` (no `buildScanStartPayload` involved) with no consent fields, then line 69 does `if (!parsed.ok) throw Error(parsed.error)`. The plan only promises to update "the three insertScanJob calls and the buildScanStartPayload call", so all three `it.each(["place_id","data_id","data_cid"])` cases would throw. That literal needs `public_evidence_consent: true, consent_policy_version: LEGAL_POLICY_VERSION` as well.

4. THE 409 RECOVERY CANNOT RECOVER — components/scan-page.tsx would receive `consentPolicyVersion` as a prop rendered once by the server component. The plan's 409 branch (`setConsent(false); setStep(4); setError(c.errors.consentStale)`) re-renders the SAME component instance holding the SAME stale prop and the SAME (old) consent copy, so re-checking the box posts the identical stale version and 409s again — an unbreakable loop until the user hard-reloads. The plan's stated benefit, "re-asks for consent against the new text", is not what the code would do: neither the text nor the version changes.

5. UNTESTED RESCAN CLAIM + ORDERING PIN — lib/workspace/rescan.test.ts is not in the plan. Its `vi.mock("@/lib/repositories/jobs")` insert double is `vi.fn(async (row) => ...)` and discards a second argument, so nothing would verify that `enqueueRescan` writes the consent row; the plan's assertion that "a rescan must not become a consent hole" ships with zero coverage. That file also asserts `state.inserted.audit_events[0]` is the `scan.queued` event, which pins the ordering of the two `recordNeonEvent` calls the plan adds.

6. FICTIONAL ORDERING GUARANTEE — the proposed `readScanConsent` uses `ORDER BY recorded_at DESC, id DESC`. `consent_records.id` is `gen_random_uuid()` (neon/migrations/0002_business.sql:193; lib/db/schema/business.ts:274), a v4 UUID with no insertion order, and `recorded_at DEFAULT now()` is transaction-start time, so rows written together tie and the tiebreak is random. The plan then sells this as "newest-wins, so a future granted=false withdrawal row blocks dispatch" and writes a consent-gate test for `granted === false` — but `parseScanConsent` hardcodes `granted: true` and no code path in the design can ever write a `false` row, so that test asserts a state the system cannot reach.

7. TYPE GAP — `assertScanConsent(jobId, deps: { readScanConsent; failQueued } = jobsRepository, ...)` will not compile as specified. lib/repositories/jobs.ts:5 declares `interface JobsRepository { insert(...) }` and the const is hand-typed as `JobsRepository & { readStatus(id: string): Promise<ScanStatus | null> }`. The plan adds `readScanConsent` and `failQueued` to the object literal but never says to extend that intersection annotation, so the default argument fails to satisfy the deps type.

8. IRREVERSIBLE LIFECYCLE DECISION PRESENTED AS A RISK BULLET — reusing `consent_records` is correct against the frozen catalog, but `consent_records_job_id_fkey ... ON DELETE CASCADE` (0002_business.sql:615) means the proof of lawful public-evidence collection is destroyed whenever the scan is erased. The plan concedes in its own risks and open questions that this may be wrong and is unfixable without DDL that `verifyCatalog` blocks — yet proceeds. That is an owner decision to take before rows exist, not a bullet to file.

### Risks

- JobsRepository.insert gains a second required parameter, which ripples into every hand-written test double. Concretely: lib/scan/start-job.test.ts:123 and app/api/scan/start/route.test.ts lines 59, 110, 139 and 189 use `toHaveBeenCalledWith(expect.objectContaining({...}))` with a single argument and will fail until a second matcher is added. - ScanStartPayload gains two required fields, and tests/funnel-scan.test.ts asserts the payload with exact `toEqual`, so it breaks until updated. Same for the two-argument buildScanStartPayload calls in tests/scan-start-contract.test.ts and test/integration/neon-scan-start.integration.test.ts.
- A browser tab left open across a deploy that bumps LEGAL_POLICY_VERSION posts the old version and gets 409. Handled by the new 409 branch (reset the checkbox, return to step 4, show errors.consentStale), but a tab running a pre-change JS bundle sends no consent at all and gets a generic 400 with the existing submit error. That is fail-closed and correct, just briefly confusing on deploy day.
- Strict equality against the current policy version at the dispatch gate can strand a job queued moments before a policy bump: it is marked failed with failure_category='consent_policy_stale' rather than scanned. In practice dispatch follows start by seconds, and the merchant sees the existing retry card, but it is a real (if rare) lost scan. Relaxing the gate to a set of published versions is the alternative — see open questions.
- The dispatch gate marks any queued job without a consent row as failed. After this change both writers (scan start and rescan) always write one, but a job inserted by hand or by a future ops script would be terminally failed on its first dispatch attempt. That is the intended fail-closed behaviour and should be documented next to failQueued.
- The consent row cascades away with audit_jobs (ON DELETE CASCADE, inherited from the existing FK). If the product ever needs consent to outlive an erased scan as proof of lawful collection, that is not achievable on this table without a migration — and a migration is blocked by verifyCatalog's frozen snapshot. Worth deciding now rather than after rows exist.
- jobsRepository.insert moves from a pooled drizzle call to a checked-out client via withTransaction, so it now holds a pool connection for two statements instead of one. Negligible at this volume, but it is a behaviour change on the hottest write path in the funnel.

### Open questions (human decision)

- Should the dispatch gate accept any previously published policy version rather than only the current one? Strict equality is the safest reading of 'validate policy version' but strands in-flight jobs across a bump. A `PUBLISHED_POLICY_VERSIONS` allowlist in lib/legal/policy.ts (today: ['2026-07-28'], with '2026-07-14' already documented as historical) would keep the property 'consent was given against text we actually published' while never stranding a job.
- Should a rescan record a fresh public_evidence consent (recommended here: the owner's click is the consenting act, stamped with the currently published version) or copy the parent job's row forward? The two differ visibly in the Activity feed and in any future DSAR export.
- Retention: consent_records rows cascade when the job is deleted. Is that the intended lifecycle for scan-time consent, or should proof of lawful public-evidence collection outlive the erased scan? Changing it later needs DDL, which the frozen catalog contract makes expensive.
- The CLAUDE.md wording for guardrail 13 / Phase 1 step 4 says the step-4 consent is 'recorded as a consent.public_evidence audit event'. This design records it in consent_records instead (and emits the audit event only on the rescan path, where a workspace_id exists). Confirm that substitution — audit_events.workspace_id is nullable in SQL but AuditEventInput.workspaceId is a required string, and widening it to reach anonymous funnel scans is a larger change than this item warrants.

## Bound scanning-page polling and add an honest stalled state

**Verdict: needs-change** · design touches 5 files · migration needed: false

### Recommended approach

Add a bounded polling budget (15 minutes / 50 attempts, whichever comes first) plus a tiered backoff, and turn the implicit "spin until terminal" behaviour into an explicit four-value view state (running | ready | failed | stalled) driven by pure functions in lib/funnel/scan-progress.ts. The stalled state never claims failure: it says we stopped asking, not that the scan stopped, because a scan really may still be running server-side. Re-POSTing /api/scan/process is already safe to offer as the resume action — I confirmed lib/scan/execution-store.ts's claimJob is a single atomic UPDATE whose WHERE clause matches only `queued` or a stale (>30 min, attempt_count<3) `collecting|scoring|persisting` row, and packages/scan-engine/src/processor.ts returns `{status:"already_claimed"}` with zero provider calls when the claim returns no rows, so a resume can neither create a job nor read a paid source twice. Refresh/reopen survival comes from a localStorage record per jobId holding a never-reset `startedAt` (honest elapsed) and a separately resettable `budgetStartedAt` (polling budget), so a refresh resumes the remaining budget instead of buying a fresh 15 minutes, and a returning user always gets at least one status read before any stalled verdict. The budget is also sized against the real limiter: RATE_LIMITS.scan_status is 120/hour per jobId x IP and the current unbounded 8s loop trips it at roughly 16 minutes and then spins on 429s forever; the new schedule spends ~44 reads per full budget so two page loads still fit.

### Risks

- The stalled threshold is a judgement call against real scan durations. CLAUDE.md says a live scan takes ~5-13 minutes, so a 15-minute budget covers a healthy slow scan; if real HK/TW scans regularly exceed 15 minutes, users will see the stalled card on healthy scans. The copy is written to survive that (it says we stopped asking, not that the scan stopped) and Check again is a one-click recovery, but MAX_POLL_DURATION_MS should be revisited once live timings exist.
- Resume is a genuine no-op for the first 30 minutes after the last attempt, because lib/scan/execution-store.ts only reclaims a job whose last_attempt_at is older than 30 minutes. The design handles this with copy rather than by hiding the button, so a user can click a button that visibly changes nothing. Hiding it until minute 30 would leave the stalled state with no secondary action at all, which is worse.
- The resume POST runs the scan inline (maxDuration = 300) and can hold the connection for up to five minutes. The design deliberately fires it fire-and-forget with a busy flag and lets polling remain the source of truth, so a slow or aborted POST cannot wedge the UI — but the button's busy state may linger until the request settles.
- Repeated Check again clicks each grant a fresh ~44-request budget against a 120/hour scan_status limit, so roughly the third or fourth manual check in one hour lands on a 429. That degrades into the honest stalled("rate_limited") copy rather than a spinner, which is the intended behaviour, but it is a real ceiling worth knowing.
- localStorage may be unavailable (private mode, blocked site data) or throw on access. Every read/write is wrapped, and the fallback is a fresh in-memory record, which means such a browser does get a fresh budget on each refresh — the same behaviour as today, just bounded.
- Adding "stalled" to the CollectorPhase union touches every exhaustive map over it (PHASE_PROVIDER_STATE, PHASE_ICON_CLASS, the new PHASE_ICON, and copy.funnel.scanning.phase in three locales). TypeScript catches a missed map, but the three copy objects are the ones to check by hand.
- The wall-clock budget keeps running while a tab is backgrounded even though throttled timers fire few polls, so a long-backgrounded tab can return to a stalled card for a scan that actually finished. The visibilitychange catch-up poll exists specifically to resolve that within one request, but there is a brief window where the stale card is shown before the catch-up lands.
- e2e/acceptance/public-funnel.spec.ts waits up to 120s for the ready button; fixture scans finish inside the fast (8s-cap) phase, so the new tiering does not affect it. A live scan that reaches the 90-second mark now polls every 30s, so a report can appear up to ~30s later than before on the page (the auto-redirect still fires on the next poll).

### Open questions (human decision)

- Is 15 minutes the right stalled threshold for live HK/TW scans, and is the 30-second late-phase poll cadence acceptable for how quickly the report should appear after a scan finishes? Both are single constants (MAX_POLL_DURATION_MS, SLOW_POLL_DELAY_MS) but they are product-visible.
- Should the stalled copy name the 30-minute reclaim window at all? It is honest and sets expectations, but it also exposes an internal operational number to merchants. The alternative is a vaguer 'we can pick it up again shortly' with no interpolated minutes.
- Should the elapsed line switch to minutes past 60 seconds (the proposed elapsedMinutes key), or stay as raw seconds? With a 15-minute budget the current 'Elapsed 863s' becomes common, but this is the one change in scope that is presentation rather than correctness.

## Reap action_runs stranded in running

**Verdict: needs-change** · design touches 12 files · migration needed: false

### Recommended approach

Reap in application SQL with no migration at all. `scripts/neon/catalog.ts::verifyCatalog` deep-equals `columns`, `constraints` and `indexes` against `test/integration/fixtures/legacy-final-catalog.json` with allowlists ONLY for functions and triggers (`additionalFunctions`/`additionalTriggers`) — so adding lease/expiry columns to `action_runs` (the `workspace_scan_completions` pattern) is not available without inventing new catalog allowlist machinery and desyncing `lib/db/schema/business.ts` from the frozen oracle that `neon-schema.integration.test.ts` compares Drizzle against. Everything needed is already on the table: `created_at timestamptz NOT NULL DEFAULT now()`, `started_at`, `finished_at`, and the `timed_out` value already in `action_runs_state_check`. Staleness rule: `state IN ('queued','running') AND COALESCE(started_at, created_at) < now() - RUN_STALE_AFTER_MS`, where `now()` is the database clock (matching `claim_audit_job`/`consume_rate_limit`) and `RUN_STALE_AFTER_MS = 900_000` (15 min) — 15x the platform's hard `maxDuration = 60` kill in `app/api/actions/[actionId]/run/route.ts`, so it can never reap a live handler. The whole reap is ONE statement (locking CTE -> UPDATE ... RETURNING -> INSERT INTO audit_events SELECT FROM the RETURNING), so the transition and its audit row commit together and `FOR UPDATE ... SKIP LOCKED` makes two concurrent tabs reap disjoint sets — the loser writes zero rows and zero audit events. Fencing already exists and must simply not be weakened: `actionRunRepository`'s `loadRun(client, input, 'running')` in lib/repositories/artifacts.ts rejects when `row.state !== 'running'`, so a late-arriving worker's `finish()` throws `invalid_run_transition` and writes no version, no `actions` update and no audit — no token column is needed. Retry stays explicit: the reaper only clears the run row; `canGenerate` in components/workspace/action-detail-client.tsx re-enables because `runStateKey` is now `'timed_out'`, and the owner presses Generate, hitting the unchanged POST /api/actions/[actionId]/run.

### Files the plan changes

- `lib/repositories/action-run-reaper.ts` — NEW. `import "server-only"`, `type Executor = Pick<Pool | PoolClient, "query">`, `getPool` from `../db/client` — same shape as `actionMutationRepository` in lib/repositories/action-mutations.ts. Export `REAP_STALE_ACTION_RUNS_SQL` (one statement) and `actionRunReaperRepository(client?: Executor)` with a single method `reapStale(workspaceId: string, actionIds: string[], staleAfterMs: number): Promise<string[]>` that returns `[]` immediately when `actionIds` is empty, otherwise runs the SQL with `[workspaceId, actionIds, staleAfterMs]` and maps `rows` to `run_id`. The SQL:

WITH stale AS (
  SELECT r.id, r.action_id, r.workspace_id, a.location_id, r.agent_key, r.state AS previous_state,
         COALESCE(r.started_at, r.created_at) AS stale_since
  FROM action_runs r
  JOIN actions a ON a.id = r.action_id AND a.workspace_id = r.workspace_id
  WHERE r.workspace_id = $1
    AND r.action_id = ANY($2::uuid[])
    AND r.state IN ('queued','running')
    AND COALESCE(r.started_at, r.created_at) < now() - ($3::double precision * interval '1 millisecond')
  ORDER BY r.id
  FOR UPDATE OF r SKIP LOCKED
), reaped AS (
  UPDATE action_runs r
  SET state = 'timed_out', finished_at = now()
  FROM stale s
  WHERE r.id = s.id AND r.state IN ('queued','running')
  RETURNING r.id, s.action_id, s.workspace_id, s.location_id, s.agent_key, s.previous_state, s.stale_since
)
INSERT INTO audit_events (workspace_id, location_id, actor_type, actor_id, event, entity_type, entity_id, payload)
SELECT workspace_id, location_id, 'system', NULL, 'run.timed_out', 'action_run', id,
       jsonb_build_object('locale', NULL, 'action_id', action_id, 'agent_key', agent_key,
                          'previous_state', previous_state, 'stale_since', stale_since,
                          'stale_after_ms', $3::double precision, 'reason', 'action_run_reaped')
FROM reaped
RETURNING entity_id AS run_id

Design notes to put in the module doc comment: (1) `now()` is the database clock, never a JS Date, so a skewed app instance cannot reap a live run; (2) `FOR UPDATE ... SKIP LOCKED` (the idiom `consume_rate_limit` already uses in neon/migrations/0004_atomic_operations.sql) means concurrent reapers take disjoint rows rather than double-transitioning or double-auditing; (3) the redundant `state IN ('queued','running')` on the UPDATE is the explicit fence against a row that changed under the lock; (4) `r.workspace_id = $1` plus the `a.workspace_id = r.workspace_id` join means a guessed action id from another workspace reaps nothing; (5) it deliberately does NOT touch `actions` — `queue()`/`start()` never write `action_state` (only `finish()` does), so a strand leaves `actions` untouched and there is nothing to reconcile there; this also keeps the reaper entirely clear of `completion_fence_actions`; (6) `actor_type='system'`, `actor_id=NULL` because this is a reconciliation, not a member action — the member whose page render triggered it did nothing; (7) `payload.locale = NULL` mirrors `recordNeonEvent`'s CLAUDE.md §3.11 payload contract; (8) callers must have authorized membership first (same contract as `workspaceReadRepository`).

1. Wrong precedent for the new repository's parameter type. lib/repositories/artifacts.ts:170 declares `actionRunRepository(transaction: RunTransaction = withTransaction)` — it takes a transaction runner, NOT a client — and inside queue() (line 202) `atomic(async client => ...)` hands out a `PoolClient`. ### Risks

- The actions LIST page is deliberately not reaped, so a stranded run keeps showing the 'Generating' displayPhase chip on /owner/[slug]/actions until the owner opens that action's detail page (which reaps and then reflects 'timed_out' on the next list render). Reaping in listActions/overviewsFor would turn every list render into a multi-row write. Accepted, and pinned by a test so it is a decision rather than an oversight.
- Reaping is a write performed during an RSC render of a page whose route is force-dynamic. It is one statement that matches zero rows in the normal case, and it is wrapped best-effort so a failure logs and the page still renders — but it does mean an authorized GET can produce an audit_events row. Mitigated by actor_type='system'/actor_id=NULL so it is never attributed to the reader (including a viewer).
- The 15-minute threshold is a fixed policy constant, not a per-run deadline. A future change that raises maxDuration on app/api/actions/[actionId]/run/route.ts (or moves runs to a longer-lived runtime) without raising RUN_STALE_AFTER_MS could in principle reap a still-live run. The run-reaper.test.ts invariant (RUN_STALE_AFTER_MS >= ROUTE_MAX_DURATION_MS * 5) catches the common form of that mistake, and the loadRun state fence means the worst case is a wasted run rather than corrupted output.
- Because there is no lease token, the fence is entirely the state precondition in actionRunRepository's loadRun. Any future change that makes finish() tolerate a non-'running' row (for example an 'upsert the terminal state' refactor) would silently re-open the overwrite hole. Called out in the loadRun comment and covered by the fencing integration test.
- 'timed_out' rows appear in the run history for the first time, so anything that assumed action_runs only ever holds queued/running/succeeded/failed now sees a sixth value. The UI paths were audited (runProgress, run-state box class/icon/copy, stateLabel, canGenerate, displayPhaseKey) and all already handle it; the only gap was owner-facing copy, which the action-detail-client.tsx edit closes.
- Rows stranded by earlier deploys are only cleared when someone opens that action (or starts its next run). There is no bulk backfill, by design — no cron and no second scheduler is permitted, and a one-shot manual sweep would be a paid/provider action outside this session's authority. Every stranded row is reachable through its own detail page, so no row is permanently unreachable.

### Recommended approach

Make "required input" evidence-aware with one shared server-side resolver rather than special-casing the review textarea. A new pure module `lib/workspace/evidence-inputs.ts` owns both the review selector (moved verbatim from `lib/workspace/runs.ts::sampledReviewsFromRawData`, so the page, the derivation and the agent all read the same bytes) and a tiny registry that marks an input key as already-supplied from stored data: `reviews_without_response` from `audit_jobs.raw_data`, `brand_voice` and `language` from the `brand_profiles` row. `lib/repositories/action-derivation.ts` already loads that job row (its `JOB_COLUMNS` includes `raw_data`) and the brand row, so it can pass the resolved set into `deriveActions`, which subtracts it from `template.requiredInputs` before writing `actions.required_inputs` and before `scorePriority({inputsAvailable})` — no new column, no new SQL object, no migration, and every existing consumer of `required_inputs` (overview's `missingInputs`, the PATCH readiness rule, the list card) becomes correct for free. The detail page stops guessing: `getAction` resolves the action's snapshot exactly the way `resolveActionRunContext` does (`source_snapshot_id` first, else the location's latest), reads `raw_data` through the already-scoped `artifactRepository().assistantReviewData`, and returns a `scanInputs` read model carrying the same excerpts the agent will receive plus the sample bounds; the client renders that list with an `Observed` fact type and a limitation note instead of a blank Textarea, and demotes the Textarea to an optional "add a review the scan missed" disclosure. Client text never becomes evidence: `ctx.sampledReviews` is still only ever built from stored `raw_data`, owner text stays under `provided_inputs`, and the review-reply prompt is reworded (with a `promptVersion` bump) to say which block is scanned and which is owner-typed. The fallback holds at three layers — derivation keeps `reviews_without_response` required when the selector finds nothing, the detail page keeps showing the input form, and a run with an empty sample still returns `facts_needed: ["reviews_without_response"]`, which `actionRunRepository.finish` writes back as `action_state='needs_input'`.

- Bumping review_reply's promptVersion invalidates lib/agents/__snapshots__/agents.test.ts.snap and changes the prompt_version stored on new action_runs (existing rows keep theirs). The snapshot update must land in the same commit or CI fails.
- Derivation's ON CONFLICT DO UPDATE deliberately excludes action_state, so an action that loses its review evidence gets the required input back but stays in its current state; it only returns to needs_input through the run's facts_needed path, costing one wasted model call in that rare transition.

### Risks

- Editing `legal.retentionBody` touches published privacy-policy text, and lib/legal/policy.ts:7 says `LEGAL_POLICY_VERSION` should be bumped together with a substantive change to `legal.*`. Recommendation: do NOT bump — the deleted sentence described a mechanism that never existed, so removing it narrows no user right and changes no purpose, retention, sharing or rights clause; every `consent_records` row stamped 2026-07-28 stays auditable against text that is now merely accurate. Bumping would restamp all future consent rows for a correction and would additionally require the three `funnel.trust.policyLink` strings (copy.ts:617/907/1197) and CLAUDE.md to change. Flagged as an open question because it is a legal call, not an engineering one.
- The hydrated "email channel hides the field" test drives a Radix `RadioGroupItem` in jsdom; pointer-event handling there can be brittle. It is the only interaction-dependent case — drop it rather than weakening the component for testability, since the same invariant is covered deterministically elsewhere.
- Renaming `recoveryLabel`/`recoveryHint` to `signInEmailLabel`/`signInEmailHint` is compiler-enforced across the `FunnelCopy` type and all three locale objects, so a partial rename cannot ship — but note the sole runtime consumer is components/unlock-page.tsx:172/180, and the four e2e acceptance specs use `c.unlock.channels`/`placeholders`/`contactLabels`/`deliveryTitle`/`submit` only, so no Playwright selector breaks.
- Adding `recovery_invalid` to `UnlockFormError` widens a union consumed by the component's error mapping; the nested ternary at unlock-page.tsx:67 must become an exhaustive `Record<UnlockFormError, string>` or a new code silently renders the wrong message (it would fall through to `errors.contact`).
- Deleting 39 keys × 3 files is the largest single edit here; the whole namespace occupies lines 96-136 in all three bundles, so the ranges are identical. `t()` falls back to the key string, so even a mistaken deletion of a live key degrades to visible key text rather than a crash — and tests/i18n.test.ts's shared-key-set assertion catches any asymmetric deletion.
- This change deliberately does not build a recovery flow. A merchant on a new device with no grant cookie still cannot reopen the report by email alone: they either re-run the unlock form, or sign in and become a workspace member (`authorizeReport`'s `member` branch). The new copy must not imply otherwise — hence "can request a sign-in link", not "can reopen your report".
- Sign-out revokes the viewer grant (`app/api/report-access/sign-out/route.ts`), and `isLeadRecipient` requires `revoked_at IS NULL`, so an address can stop being mail-eligible. The proposed copy makes a capability statement rather than a guarantee, and the sign-in page already hedges with "if the address is eligible" — do not add an absolute or time-bound promise to the hint.
