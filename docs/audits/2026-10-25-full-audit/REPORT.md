# smeassistant full repository audit

Audit date: 25 October 2026, America/New_York. Repository: [YNWAforever/smeassistant](https://github.com/YNWAforever/smeassistant). Baseline: `85dbcd6cdfecbecad450977c5d9b9d5a732f94a5`. Patch branch: `fix/audit-p0-cleanup`.

The audit found **3 P0, 5 P1 and 8 P2 findings**. The patch addresses all three confirmed P0 code risks: production TLS parser bypasses, forbidden self-service ownership, and unsafe application website requests. P0 ownership and TLS exposure depend on runtime configuration; this audit does not establish that those unsafe configurations are deployed. Dependency advisories remain a **P1 release blocker**, even after the P0 patch.

## Implemented safe P0 fixes

- **F01:** Production database URLs reject duplicate TLS controls, nested `connectionString` and weak libpq certificate semantics. Every accepted production URL is serialized with an explicit `sslmode=verify-full` before pg parses it, including percent-encoded keys mixed with malformed escapes or spaces. Tests inspect the installed driver's effective SSL settings for both application and migration URLs. Local disposable plaintext PostgreSQL remains supported outside production.
- **F02:** Removed the email/grant ownership mutation branch, its runtime flag wiring and ownership-only dead helpers. Sign-in can resume already verified ownership; it cannot create or attach a workspace from a report recipient's email or grant, even with the obsolete flag set true. Google verification and staff assignment remain the ownership paths. Integration fixtures use the reduced read-only claim contract; obsolete tests asserting unsafe success were replaced.
- **F03:** Workspace snapshots and scheduled verification use application-owned public-address validation, socket pinning and manual per-hop redirects. Streams stop at 512 KiB, HTML content type is required, and the enclosing execution budget/deadline covers DNS, headers and reads. Public HTTP remains supported; no credentials or cookies are sent. Native requests ask for identity encoding and treat unexpected compressed bytes as unavailable. Final URL, all fifteen check keys, coverage semantics and persisted result shape remain intact. Vendored transport/scoring files were not edited.

The application safe fetch is adapted from the existing pinned engine transport. A broad shared-transport refactor was avoided to keep the vendor boundary unchanged. Refused private URLs, oversized responses and servers ignoring identity encoding now produce unmeasured evidence instead of partial or invented check failures.

## Dependency findings

`pnpm audit --prod --json` reports **45 vulnerability instances** (5 critical, 20 high, 18 moderate, 2 low) across 582 dependency nodes, represented by **42 advisory records**. [DEPENDENCY-ADVISORIES.csv](DEPENDENCY-ADVISORIES.csv) records every advisory's installed/range/fix information, URL and applicability. These are inventory severities, not 45 proven exploits.

Next `16.2.6` has Server Action DoS advisories whose application preconditions exist in `app/[locale]/owner/actions.ts`. The audit snapshot's current fixed floor is Next `16.4.1`; coherent renderer review includes sharp `>=0.35.5`. The five critical Next records need specific conditions: Windows hosting, attacker-controlled SVG values in Node OG generation, particular cache functions, or attacker-controlled optimizer input. Source review did not prove those critical exploit paths. The image optimizer remains enabled despite no `next/image` imports; remote input is limited to `images.pexels.com`, while local optimization input is not explicitly restricted. This deserves a release gate and a controlled dependency patch, not a claim that unused image components remove exposure.

Direct evidence decoding rejects unsupported formats before `image-size`/Sharp, which mitigates several codec advisories in that path. It does not cover Next's separate optimizer. Tooling packages in the production graph arrive transitively through the pinned Neon SDK; their presence alone does not establish a running production Vite/Vitest/esbuild service. The explicit Neon SDK pin stays unchanged pending deliberate compatibility review.

The registry scan initially met automatic-review rejection for dependency metadata disclosure. GitHub's `private:false` repository metadata and unchanged public manifests established that the requested audit sends public package/version data; a supported retry was approved and completed. No advisory check remains blocked for approval.
